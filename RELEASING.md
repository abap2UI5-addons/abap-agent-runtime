# Releasing

One tag, one push: **`X.Y.Z`** on `main`. Everything mechanical lives in
[`.github/workflows/release.yaml`](.github/workflows/release.yaml); its
header comment is the reference. This file is the human checklist and the
part no workflow can decide.

**There is no release yet.** `main` and the generated `standard` / `cloud`
branches are what users install today, the addon is experimental and its
API may still change (README, "Status"); the first tag will be **0.1.0**,
and until 1.0.0 a minor version may change the API - CHANGELOG.md says
where. The version in the tree is always the *next* release
(`package.json` and `z2ui5_if_agent_app=>version` say 0.1.0 now), so cutting
it is the checklist below with step 2 skipped.

## What a release is for

Merging to `main` is the release for anyone reading the repository, and for
abapGit - a pull of `standard` or `cloud` installs what is there,
regenerated by `publish-branches.yaml` from every push to `main`. A tag is
for everyone else: it is the only thing in this repository that does not
move. A system that pulled `standard` on Monday and another on Tuesday may
run different code without anyone having decided that, and a bug report
without a version number cannot be read.

The version is also what abapGit shows for the installed repository:
`.abapgit.xml` names `Z2UI5_IF_AGENT_APP=>VERSION`, so an administrator sees
`0.1.0` next to the repository, not a commit hash.

## How reversible is it?

A tag can be deleted and re-pushed and a GitHub release edited. In practice
a tag that existed for an hour has been fetched by somebody's CI or pulled
into a system, so treat a published version as final and fix forward with
the next one.

The one thing that cannot be fixed forward is a **wrong version number in a
system**: `z2ui5_if_agent_app=>version` is what abapGit displays. `npm run
check:version` holds it to `package.json` on every push, and `npm run
check:release` holds both to the changelog before a tag.

## Cutting a release

1. **`CHANGELOG.md`** - move the entries under `## Unreleased` to a new
   heading, newest first:

   ```
   ## Unreleased

   ## 0.1.0 - 2026-10-20
   ```

   The workflow publishes exactly this section as the GitHub release notes,
   so what is written here is what everyone gets told changed. For 0.1.0,
   replace the **No release yet** paragraph at the top of the section with
   one that says what the release is (experimental, the API may change
   before 1.0) - it would otherwise be published as written. Keep the (now
   empty) `## Unreleased` heading standing above it - every change points at
   it, and `check:version` fails without it. The heading format is
   `## X.Y.Z - YYYY-MM-DD`, nothing else; the gate reads it.

2. **Bump both version numbers** - `package.json` (and `package-lock.json`,
   `npm version --no-git-tag-version X.Y.Z` does both) and the `version`
   constant in `src/01/z2ui5_if_agent_app.intf.abap`. Two files on purpose
   (one ships into the system, one does not), and nothing but the gate
   keeps them together. Before 1.0.0: a change of the API (the opt-in
   interface, the tool arguments, the settings) is a **minor** bump and a
   changelog entry that says so; fixes are a patch.

3. **Check, then merge:**

   ```sh
   npm run check:release          # the two versions and the changelog agree
   npm run check && npm run unit  # what the release job runs
   ```

   Commit (`Release 0.1.0`) and merge to `main` through a pull request like
   any other change; the push workflows run on it, and `publish-branches`
   regenerates `standard` and `cloud` from the merged commit.

4. **Wait for `publish-branches` to finish green**, then tag the merge
   commit on `main` and push the tag by name:

   ```sh
   git checkout main && git pull
   git tag 0.1.0
   git push origin 0.1.0
   ```

   By name: `git push --follow-tags` pushes annotated tags only, `git tag`
   without `-a` makes a lightweight one, and the push then reports nothing
   and no release runs. The release job refuses a `standard` or `cloud` head
   that was not generated from the tagged commit (its commit message names
   the source) - a stale branch fails the job with a message saying to wait
   for `publish-branches` and re-run, instead of tagging stale content.

5. **Watch the run.** It re-checks everything on the tagged commit (the
   gate, `npm run check`, `npm run unit`, the 7.02 downport lint), prints
   the release notes, creates the `X.Y.Z` release and then tags the two
   branches `X.Y.Z-standard` and `X.Y.Z-cloud`, each with a release of its
   own that points back at `X.Y.Z`. abapGit installs from a tag like from a
   branch, so a system can pin what it pulled.

There is no dry run of the workflow itself: it runs on a pushed tag only
(no branch push, no manual dispatch), so nothing in it can publish from a
branch. The rehearsal is step 3 - `npm run check:release`, `npm run check`
and `npm run unit` are the checks the job runs before it publishes, and the
7.02 downport lint is the `ABAP_702` workflow on the merge commit.

## What the workflow does NOT decide

- **When to release, and what the number is.** Nothing computes a semver
  bump from the diff. Before 1.0.0 the rule above (API change = minor) is
  the whole policy; 1.0.0 itself is the promise that the opt-in interface,
  the tool arguments and the snapshot extension are stable, and it is cut
  only when a real system has run the addon for a while.
- **Whether `main` is worth releasing.** Green gates say the tree agrees
  with itself and runs on the transpiled runtime, not that it is a good
  moment, and not that it was pulled into a system - `npm run unit` is not
  a system (abap2UI5's `abap-check` skill lists what the transpiler cannot
  see). A pull of the release candidate into one system per platform before
  the tag is good manners, and the only check for the activation errors
  the catalogue describes.
- **The reference.** The snapshot is a contract with abap2UI5/mcp-server and
  abap2UI5/protocol (AGENTS.md, "The snapshot is a contract"). A release
  does not move the parity base; porting a reference change does, and the
  changelog entry names it.
- **The dependencies.** abap2UI5 and headless-frontend are installed first
  and versioned on their own; README names the oldest abap2UI5 release the
  addon needs when one is known. The unit job builds against their `main`.

## After a release

- **Nothing is published anywhere else.** No npm package, no docs page, no
  registry: the tag, the three GitHub releases and the branch tags are the
  whole output.
- **A system that wants to pin** pulls `X.Y.Z-standard` or `X.Y.Z-cloud` in
  abapGit instead of the branch; the README's install table names the
  branches for a moving install and the tags for a fixed one.
- **The next change** goes under `## Unreleased` again, and the version in
  the tree stays at the released number until somebody bumps it for the
  next release (step 2) - `check:version` only asks that the two files
  agree and that no changelog section runs ahead of them.
